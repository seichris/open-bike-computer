## Finding ledger

### OTM-001 — P2 — Bind the OTA intent before asynchronous preparation

**State: fixed+verified.**

On the baseline, `FirmwareUpdateManager.installLatest` validates the selected device, awaits maintenance eligibility and image download, and only then writes `bleManager.connectedDeviceID` into the pending update. `BLEManager.connect(to:)` permits selecting another registered device during that interval: `beginFirmwareMaintenanceReconnect()` pauses ordinary sync but does not acquire a device-operation lease. `DeviceTransferManager.prepareFirmwareMaintenance` therefore captures the replacement device when it finally starts.

Trigger: begin an update on owned device A, then connect owned device B while the image download is in flight. If B supports OTA, has the same target and has an older build, the app can request maintenance and continue the update on B. An incompatible target can still be unnecessarily rebooted before device-side admission rejects it. This is an intent/identity race for a multi-device owner, not a bypass of firmware signature verification or BLE ownership.

Baseline locations: `FirmwareUpdateManager.swift:393` (`installLatest`), `:890` (`persistPendingUpdate`); `BLEManager.swift:3613` (`connect(to:)`) and `:6235` (`beginFirmwareMaintenanceReconnect`); `DeviceTransferManager.swift:1608` (`prepareFirmwareMaintenance`).

The local regression uses the actual manager and BLE command endpoint with a paused URLProtocol response. A HOST_TESTING-only seam fills the already-verified manifest cache with synthetic metadata; it neither changes the production verifier nor uses a release private key. The baseline exited 1 with `only the original live connection may enter firmware maintenance after download: expected false, got true`. The emitted maintenance command is the directly observed failure; continuation through upload is established by the source path, not by flashing hardware. The Settings device screen's "Set as current device and connect" action reaches this path while the firmware download is busy. Additional cases cover selection before the scheduled task starts, selection during eligibility, same-device connection replacement during download, and an unchanged connection reaching maintenance.

Repair: capture device identity and connection epoch when install is requested; recheck after preparation awaits; require those same values at maintenance admission, including after awaited cleanup; persist the original identity before downloading; preserve the existing correlation-checked maintenance reboot and subsequent transfer-session binding.

### OTM-002 — P2 — Recover interrupted local preparation without creating remote uncertainty

**State: fixed+verified.**

An app exit while a pending update is explicitly `downloading` or `image_verified` leaves a durable record before any maintenance command. On baseline relaunch, `reconcilePendingUpdate` has no branch for those stages: with the old running image and no maintenance correlation, it converts the record to `unresolved`. `installLatest` rejects that record on every retry. A failed local download can similarly become unresolved on later status reconciliation. This can block future OTA despite the device never receiving an update command.

The HEAD manager failed the relaunch regression with exit 1: `only a known local preparation is cleared on relaunch: downloading: expected true, got false`.

Baseline locations: `FirmwareUpdateManager.swift:801` (`reconcilePendingUpdate`, final fallback at `:864`), `:997` (`runBusy` failure handling), and the pending-operation admission guard at `:396`. This was discovered while checking OTM-001's retry behavior during the first repair batch.

Repair: distinguish explicitly local stages, discard them on relaunch or local failure, and keep failures visible to the user. Local recovery does not discard records with a maintenance correlation, a required operation receipt, a missing legacy stage, or a stage at/after a maintenance request. Serialize busy operations so a repeated install cannot mutate another active preparation's record. Tests exercise actual persisted relaunch with both legacy missing device IDs and bound identities, remote-stage preservation, contradictory remote evidence, and repeated install attempts during a paused download.

## Key handling and recovery interpretation

Firmware release verification has an embedded public key shared by firmware and app. Map-stream signing uses a separate P-256 trust registry with key IDs and fingerprints. The production registry has two trusted production public keys; development fixture scalars are rejected, and a development key is compiled only into explicitly permitted development firmware. No production or user private key was read or exported; cryptographic tests use synthetic fixtures.

The firmware signing-key migration document describes an earlier operational migration. That history does not establish the current state of the GitHub signing environment. Firmware-key rotation still requires a release/device migration; map-key rotation requires overlapping compatible readers and delivery policy. Neither a catalog emergency switch nor retirement metadata can revoke bytes already installed offline.

For OTM-001/002, the pending download retains the original device identity while active. A stale or failed local preparation ends without a device command and is removed, permitting a deliberate retry after selecting the intended connected device. Once a maintenance/finalize action may have reached the device, existing unresolved-state reconciliation remains necessary; do not erase its receipt to force a retry. Reverting this change would bring back the demonstrated defects, so repair forward if a regression is found. Recovery for a bad app build is a corrected App Store/TestFlight build. Firmware, the BLE protocol and the server are unchanged, so no device or backend rollback applies.
